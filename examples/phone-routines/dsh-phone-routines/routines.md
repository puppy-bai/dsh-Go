# 任务操作卡

以下是流程模板，不是硬编码的平台适配，也不是运行成功证明。先用实际工具目录核对参数；若 `run` 的 schema 不一致，以当前工具为准。

## 一、测试页表单

在 `phone-lab.html` 中让模型读取“姓名输入框”“城市输入框”“学习目标输入框”，填入“测试同学”“上海”“每天练习三题”，点“保存测试表单”，再查“表单已保存”。Chrome 的包名一般为 `com.android.chrome`，但必须先用 `screen` 回读确认；不能照抄到其他浏览器。

```json
{
  "app": "com.android.chrome",
  "dryRun": true,
  "steps": [
    {"op":"type","target":"姓名输入框","text":"测试同学"},
    {"op":"type","target":"城市输入框","text":"上海"},
    {"op":"type","target":"学习目标输入框","text":"每天练习三题"},
    {"op":"tap","target":"保存测试表单"},
    {"op":"assert","text":"表单已保存"}
  ]
}
```

`dryRun` 只做计划检查，不证明能找到输入框。验证通过后用相同计划移除 `dryRun`，再核对返回的 `completed`、`trace` 和最后页面。失败后先读屏，不从第一步整段重放；按 `nextStep` 对照现场重新规划未完成部分。不要宣称当前已具备跨重启断点续跑或答案自动备份。

## 二、有边界的视频浏览

示例请求：“打开视频 App，浏览最多 5 个视频，每个停留约 8 秒，记录可读标题，最后给我摘要。”

先确认 App，`open` 后 `screen` 读标题；取不到标题时才截图。每次 `scroll`/`gesture` 翻到下一条后等待页面稳定，确认标题变化，再计数。视频表面可能是独立播放器，不能把列表滚动返回成功当成已切视频。出现直播、广告、外部链接、登录页或连续两次没有变化，停止当前段。看不到字幕/听不到音频时，只能总结可见标题和画面，不能编造视频完整内容。

`gesture` 一次最多 10 步，但不要预先盲滑 10 屏；动态视频页应逐屏观察。`run` 中的 `wait` 能减少为短等待重复询问模型，但整段仍须有次数和时间上限。

## 三、读消息与准备回复

示例请求：“读取张三最近三条未读消息，准备简短回复，先不要发送。”

确认联系人和对话标题；只读指定范围。把草稿写进正确输入框后回读，报告“草稿已准备”。用户明确要求发送时，发送前再次读联系人、正文和按钮，按现有机制确认，发送后核对消息气泡是否出现。群聊应核对群名及是否 @ 指定成员，不能只核对同名联系人。

“自动回复新消息”需要通知监听或持续触发、联系人允许名单、去重与冷却时间、会话归属校验和人工接管。这些机制当前不由本技能提供。可以先用“当前任务内检查一次指定对话并准备回复”验证，不能把循环打开消息页宣传为全天候自动回复。

## 四、每日签到

示例请求：“打开指定 App 的签到页；如果今天已签到就返回，否则完成一次并核对结果。”

读“已签到/今日已完成/连续天数”等文字。已完成则不点；未完成且任务允许时点明确的签到入口，再检查“签到成功”或状态变化。抽奖、付费补签、授权、看广告领取等是分支，不属于普通签到，停下说明。当前手动启动任务可测试，后台定点执行另需触发机制与手机可用条件。

## 五、练习题与作业

示例请求：“在测试页解答 3 道练习题，先解释，再填写并核对，不操作真实考试平台。”

先读清题干、题号和选项。看不清则读图或请用户补充，不能猜缺失条件。求解和输入分开记录：模型给出答案→定位对应题号的输入框→填入→回读→检查本题反馈。换页后先核对题号。真实作业提交前展示准备的答案及不确定项，按用户授权和现有确认机制处理；练习结果与正式提交分开记录。

## 六、可复用的失败处理

| 现场 | 下一步 |
|---|---|
| 文字重复命中 | 重新读屏，使用最新编号；不猜第一个 |
| 滚动没变化 | 停止循环，检查列表、方向或是否到末尾 |
| 页面出现弹窗 | 先读弹窗；不把关闭位置当成原按钮 |
| App 包名变化 | 停止这一段，重新确认任务目标 |
| 点击超时 | 先读屏，确认可能已经执行，不自动重发 |
| 输入回读失败 | 保留现场，说明失败，不继续点发送/提交 |
| 任务中止/锁屏 | 不做补偿点击，解锁后重新观察再规划 |
